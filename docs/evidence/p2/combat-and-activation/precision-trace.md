# F6 menu recovery diagnostic contract

The owner reported that source `3c1b6711907b76497b7958c8c9ecfcf8227bc3fb` enters first person with F6, but F6 does not return after opening and closing a menu; native controller POV recovers the view. The cause is **unconfirmed**. In particular, the current sink clears F6 ownership on a native Toggle POV down edge without checking menu focus, and other possible causes include provider prerequisites, hard-special state, first-person observation, mapped input and fresh-press suppression. The existing log cannot distinguish them.

`precision_trace.h` supplies a diagnostic-only numeric record format and a maximum of 64 records. The integration owner must opt in explicitly, record only relevant menu/F6/native-POV event boundaries, and avoid recording menu names, raw input strings, save names, forms or unrelated controls. Gate startup events so a session can capture the actual test. The proposed integration is not wired by this commit; neither the record helper nor its test changes camera behavior.

State bit mask: bit 0 `enabled`, 1 `prerequisites`, 2 `world`, 3 `special`, 4 `menu`, 5 `firstPerson`, 6 `hardSpecial`, 7 `owned`, 8 fresh-press `armed`, 9 fresh-press `down`. Each record has before/after masks, a fixed numeric event ID, device class, pressed/edge flags and a `ToggleRequest` decision when applicable. In particular, record ownership transitions and Toggle POV edges even during menu focus, plus F6 suppression/mapping/freshness decisions. A lack of an event is not proof of its cause; the trace needs an exact candidate and a bounded reproduction.

The helper's bit encoding, truncation behavior and 64-record limit were exercised in the portable `precision_trace_test.cpp` (**PASS**). Native Windows compilation, trace wiring and runtime use remain **NOT_RUN**. Diagnostic output must be recorded with the exact INI, source and binary hashes and disabled for ordinary operation.

The Camera input and menu sinks now wire this diagnostic behind `[Debug] iPrecisionTrace=1`; absent or other values leave tracing disabled. The process-wide budget is atomic and caps output at 64 records. Tracing records only the selected boundaries and uses the existing log function; no per-frame trace or unrelated key text is recorded. This wiring has portable policy/format tests PASS, but Windows compilation and runtime verification remain NOT_RUN. It is diagnostic and does not by itself change ownership behavior or establish the root cause.

Following the menu-deferral retest failure, the diagnostic adds numeric camera state and separate mount, killmove, swim, missing control interfaces, script/beast/FOV and inactive-third-person flags. These are bounded snapshots, not proof of cross-thread atomic ordering. A bounded resume prototype was evaluated but removed from the candidate: SKSE task processing drains the queue in one pass, so self-rescheduling cannot safely observe successive frames, and a Tween state alone does not prove transition origin. Portable policy/trace tests PASS. The expanded trace's Windows build and gameplay are NOT_RUN.

Pinned SKSE source commit `7ff865f4a27d6dc936ab5fd0533ff2d706c8f857` `skse64/Hooks_Threads.cpp` (SHA-256 `15f9018b40b6037da397adc2d303957412fab165059eee153b23fdf792caa6fb`) drains the task queue until empty, with a task's `Run()` occurring before the same queue is rechecked. A task that immediately requeues itself can therefore run repeatedly in the same drain without a camera/frame update; this is not a safe next-frame observer. The source also has two processing hook sites and does not establish callback thread affinity. A `kTween` ID alone is not unique to menu return; it is used in other transitions. A safe, bounded observer or an origin-bearing signal remains unresolved. Do not ship a blind grace period or self-requeue polling loop as a fix.
