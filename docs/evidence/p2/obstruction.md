## Source findings

The inspected SmoothCam source checkout is commit `e0afd09aff26e5849dac461252e5bffbd5b69d62`, clean at inspection. This is a source audit, not proof that its build exactly matches the pinned binary. The pinned runtime/provider identities are in the [runtime matrix](../../compatibility/runtime-matrix.md) and [dependency lock](../../compatibility/dependency-lock.md).

- `SmoothCam/source/camera_states/thirdperson/thirdperson.cpp` interpolates a pre-collision position, runs provider collision rays, sends the collision-resolved `finalPos` to the camera, then stores the pre-collision position as its current position. The collision hit and result are local; the V3 API exposes no obstruction event, hit normal or resolved distance. Source SHA-256 `6ddaba9797fc661889584729f32f47a19ca0eddcdabae3f884722dc6972cefdf`.
- `SmoothCam/source/modapi.cpp` returns the provider's stored `GetPosition()` for `GetLastCameraPosition`; `SmoothCam/source/thirdperson.cpp` returns `lastPosition`, assigned from the previous `currentPosition` at the start of the provider update. It is not a collision-resolved camera position. SHA-256 respectively `9cdcc44b4e026bca1a92a6f3428271e72f5df9e9f79ea104c73818d22b04bdf2` and `2e9b5a3adad2b865b6c58a1829782f8bd098bf53d98f778061d94d91b77dbb03`.
- `SmoothCam/source/camera.cpp` writes the resolved position to the camera root, but `hooks.cpp` invokes the previous native update before the outer provider update. The current adapter's update hook sits within that chain. A comparison of the API value with the root without aligning frame and update order can mistake player movement, camera interpolation, native updates or a POV transition for obstruction. Source SHA-256 respectively `f4418072a11fb7ab2924aa4789735ff2814d24204454f6178da92e8663dd506a` and `57830a7fef128d3acdfba1cd8c04188258da3970f77cdd7082b0fa6be0666074`.
- `GetGoalPosition` is a provider goal computed from the current target, offsets, pitch and zoom; the gap to an interpolated position can exist in unobstructed motion. It is not a collision flag. Even a correctly timed displacement alone does not classify a low ceiling versus a wall or guarantee that changing pitch will improve visibility.

Consequently no unverified automatic pitch or distance controller has been introduced. The existing state precedence remains disable/invalid world/special/menu/first person/precision/targeting/obstruction/normal; any future intervention must release on higher-priority states and must not take transform ownership from SmoothCam or override F6/F8.

## Follow-up: provider smoothing and safe query limits

The pinned SmoothCam source's defaults enable world, local, Z, offset and zoom interpolation. The committed partial provider configuration leaves these at those defaults. In the inspected third-person implementation, interpolation produces the desired **pre-collision** position; the collision hull cast subsequently sets the resolved camera position. Thus these settings do not establish post-collision hysteresis or smooth recovery. Repeating the defaults in configuration would not change behavior, and no such change has been made. The bounded Phase 1 interior route above remains prior evidence, not proof for the later held-pitch adapter.

The pinned Address Library 13 maps AE ID 33007 to executable RVA `0x5574f0`. The inspected SmoothCam source calls this engine camera collision function with the camera's collision context and cell physics world. Disassembly of the exact executable shows a write through the context to a nested float before the collision operation. Its full side effects, locking and reentrancy are unverified. Calling it a second time as a purported read-only obstruction probe may interfere with SmoothCam; no such call is implemented. In addition, measuring clearance only toward an already-shortened view cannot determine whether the preferred path is clear and risks near/far cycling. A signal for the unadjusted preferred path and its timing must be validated before driving an automatic adjustment.

SmoothCam also exposes `toggleUserDefinedOffsetGroupKey` and a `userDefined` offset group. The inspected source accepts keyboard and gamepad codes and selects the group before ordinary exploration and combat groups, with normal provider offset interpolation. This is a possible **manual** close-framing option, not obstruction detection. The group can override bow/magic framing, and the provider handler does not check Skyrim's control map before accepting the key. No controller button has been proven free in the current controller-only setup, so enabling it by default would risk duplicate input or combat regressions. Any opt-in alternative needs explicit combat sub-offsets, input conflict checks and gameplay verification.

An alternative diagnostic alignment is to wrap the provider's *outer* third-person update after its deferred hook is installed, call that provider update first, and compare the provider's `lastPosition` with the camera root saved after the preceding outer call. In the inspected normal path, the provider copies `currentPosition` to `lastPosition` during its update, then writes the new collision-resolved camera root; its subsequent local-offset routine does not modify the root. This arrangement can capture both values from the same prior provider update without assuming an independently incremented frame counter. It is still a **hypothesis**: provider early returns and state/focus/ownership changes must invalidate pairs, `pitchZoomAfterInterp` must be accounted for, and the inspected source has not been proved byte-identical to the pinned DLL. Installing an outer hook also changes the current hook-integrity check, which expects SmoothCam itself in the vtable; the integrator must explicitly validate the chain and initialization order. This is a potential instrumentation path, not a measured collision signal or an implementation.

An outer wrapper cannot itself prove the provider actually advanced: its public interface has no update-generation or `ranLastFrame` signal. In the inspected source, `PreGameUpdate` may short-circuit for a requested transition, and `UpdateCamera` may return before updating if the render camera or target is missing or choose no active camera. A valid player/world check does not establish all of those internals. After such an early-out, a previously returned provider position and the native-updated root can diverge without any collision. A diagnostic wrapper can record controlled, uninterrupted runs and exclude evident transitions, but must not treat all residuals as reliable obstruction events. Its installation would need to verify that the saved predecessor is in the exact pinned SmoothCam module, change the existing vtable-owner check to recognize its own outer wrapper while retaining that predecessor validation, preserve exactly one predecessor call, and fail closed on later hook changes. A fixed-size buffer and tracked export avoid frame-loop disk I/O. This extra hook is not warranted for a shipped automatic controller without a verified provider-progress signal and pinned-binary runtime evidence.

## Independent point-query audit — diagnostic candidate only

The pinned CommonLib headers expose `TESObjectCELL::GetbhkWorld()` and virtual `bhkWorld::PickObject(bhkPickData&)`; the input, output and collector pointers are caller-supplied. Inspected SmoothCam source uses this separate point-pick path for crosshair/projectile-path queries, while its normal camera collision still uses the separate swept-hull camera caster. This is a possible way to collect **point-ray diagnostic evidence without reusing the Camera's collision context**; it is not proof that the call is side-effect-free, equivalent to the camera hull, or safe to run in another hook. Inspected `raycast.cpp` SHA-256 `67f0a05d38ef2dece6cc418c0127caa31ac887ecdefc8a7554f54ebf4e938e04`; `crosshair.cpp` SHA-256 `fd49e7b18920b91d8d7be083a0d53c91392dc098285fcf2dd77038b1a5da929c`. This source is an audit reference, not a verified source build of the pinned provider binary.

For the pinned executable SHA-256 `846efccf0c1374d71f892907f46549560f2fcb0a75cb87a3eed438baa0f1402f` and Address Library 13 SHA-256 `8aab3dd251d135b849bd983f86a4a205c920fa3e81f8e30c0e63ccfef9423842`, dense format-5 AE ID 238918 resolves the `bhkWorld` vtable to RVA `0x1a7cda8`; slot `0x33` points to RVA `0x104be80`. Read-only disassembly of that function shows an early return that writes `pickFailed` in the caller's pick data before returning false, and a normal path with conditional acquisition/release of a lock before a world ray cast. Thus `false` is not a sufficient clear-space signal; externally taking the same lock without verifying recursion and the engine's conditional path may deadlock. This limited disassembly is not a full thread-safety or lifetime proof. CommonLib maps `TESObjectCELL::GetbhkWorld()` to AE ID 18995 (RVA `0x2be9b0`); no pointer obtained from a cell or physics world should survive the guarded frame or cell transition.

Collision layers, player self-hit filtering, units, query origin and current provider goal each need runtime calibration. TDM's inspected projectile aiming code uses an explicitly locked world cast with a different pick filter (`kItemPick`), not proof of the camera hull filter or of lock safety at this call site. A point hit may correspond to geometry the camera hull ignores; a point miss cannot certify that a swept camera hull fits. `GetGoalPosition` uses the provider's *current* interpolated offsets and zoom; after an adaptive adjustment, it cannot by itself test the original preferred framing. Do not interpret point-query hits or misses as an automatic obstruction/clearance state, or use them to release hysteresis, until these mismatches are resolved and the exact binary and fixtures have been validated. No point query was wired, built or run in game in this audit.
