# Phase 5 research — targeting, lock-on and fixed-height camera

Desk research and source audit, **2026-10-28**, against main `abd5735`; revised the same day after the senior review of PR #24 (BTPS scoring, TDM disable-lease timing, Disocclusion runtime facts, licensing boundary). This is an engineering assessment of the owner's Phase 3+ requests recorded in the [Phase 2 gate](../evidence/p2/gate.md#phase-3-owner-requests). **Nothing here was built or run in game.** Facts marked *source* were read in the local provider checkouts under `session-20261026/targeting-audit` (SmoothCam 1.8.1, TDM 2.3.1) and `session-p2-20261026/commonlib-7.2.0`; facts marked *web* come from public repositories and are cited at the end; **unverified** means neither.

## R1 — Proximity activation: reuse BTPS

**What exists.** Better Third Person Selection by Shrimperator (Nexus 64339; source on GitLab). *Web:* 0.9.0 (2026-10-02) is built on CommonLibSSE-NG, handles the 1.7.99+ vtable shift and the author states 1.7.99/1.7.104 tested; 0.8.9 is the 1.5/1.6 build. Licence changed to **GPL-3.0-or-later** on 2026-10-02. Requires Address Library, **JContainers** and MCM Helper.

**How it selects.** *Web (source read by the research agent, `src/FocusManager.cpp`):* it gathers references within 200 units of the player and computes a priority of roughly `distance/range × 1.0 + angleDifference/0.5 × 5.0 + type × 0.1 + specific × 0.2 + value × 0.5`, minus small bonuses for the native crosshair target and the previous selection; the lowest priority wins. The angle term measures the object's direction against the **camera forward vector**, with `fMaxAngleDif` (default 0.5) as a cut-off. Occlusion is tested with hull raycasts **from the player's body**, not from the camera, so an elevated camera does not hide a bench behind the camera ray. Cycling walks the sorted list (`iCycleUpKey`/`iCycleDownKey` with a modifier, rebindable to gamepad codes, optional wrap); the cycled object sticks until out of range.

**Nearest-first is not the default behaviour.** Raising `fMaxAngleDif` to 2.0 only removes the angle *cut-off*; the angle weight, type, value and selection-history bonuses still contribute, so a farther object straight ahead of the camera can outrank a nearer one off-axis. A strict nearest-first configuration therefore has to set every non-distance weight and bonus to exactly zero (angle, type, specific, value, crosshair and previous-selection bonuses; a small residual preference can still reverse two objects at similar distances), establish a deterministic tie-break, and be **demonstrated** with fixtures that place a nearer object off-axis against a farther object directly in front of the camera and two objects at similar distances. Whether BTPS's configuration surface exposes every weight is **unverified** (the research agent read the formula, not the full config schema); if a weight is hard-coded, strict nearest-first is FAIL/BLOCKED pending an owner decision between accepting proximity-biased behaviour and an upstream change. The plan requires strict nearest-first for PASS and uses cycling for the cases where the closest candidate is not the wanted one.

**How it injects.** It patches `CrossHairPickData::Pick` (AE ID 26127 at a fixed offset) so the engine's own crosshair target becomes BTPS's choice. Activation, prompts and QuickLoot therefore follow it without further hooks. It also hooks `PlayerCharacter::UpdateCrosshairText`, `ActivateHandler::ProcessButton` and `HUDMenu::PostDisplay` for its widget; it hides the widget during TDM lock-on through the TDM API.

**Fit with SkyCRPG.** SmoothCam does not override the pick (it calls `PickCrosshairReference` and reads `collisionPoint` for its 3D crosshair), so BTPS and SmoothCam coexist as they do for ordinary users. The Camera module never touches the pick. The bench case from the Bannered Mare route is exactly the case BTPS was written for; how its angle weighting behaves under a 55° held pitch, where the camera forward vector points down at the player, is **unverified** and is one reason the nearest-first configuration above must be proven rather than assumed.

**Gaps.** No API to push an external target or to read the candidate list (its V0 API only reports enabled state and hides/shows the widget). Cycling is key-driven only. A second plugin cannot patch the same `Pick` offset without conflicting, so R2 must go through BTPS (fork or upstream) or replace it.

**Alternatives examined.** QuickLoot IE/EE, Simple Activate, SmartHarvest, Simple Sit, Use or Take: none select targets; they consume the crosshair reference or add hotkey actions. TDM target lock is actor-only. SmoothCam's 3D crosshair still follows the camera ray.

## R2 — Cursor mode: original work on top of BTPS

**What exists.** *Web:* nothing provides a free gameplay cursor or a stick-driven world reticle. Precedents for stick-driven gameplay overlays are Wheeler (BSD-3, ImGui over D3D11) and powerofthree's PhotoMode (GPL-3, ImGui). Cursor Unbound only smooths the menu cursor. A Scaleform menu flagged `kUsesCursor` shows the native cursor but no mod uses it for world picking.

**Mechanics available.** *Source:* `RE::CrosshairPickData` exposes `target`, `targetActor`, `collisionPoint`, `targetCollider` and the `pickCollider` phantom; the native pick is a camera-origin hull ray (`fActivatePickRadius`, `fActivatePickLength`) through `bhkWorld::PickObject`. `RE::MenuCursor` carries `cursorPosX/Y`; `NiCamera::WorldPtToScreenPt3` and the inverse ray helpers exist in CommonLib. The Camera module already owns the third-person look hook, so consuming right-stick/mouse deltas while a cursor mode is active is a policy change, not a new hook.

**Design consequence.** On keyboard/mouse the pointer currently drives yaw. A hover cursor therefore needs either a toggle (same as the controller hotkey) or a CRPG-style "hold right mouse to rotate, pointer otherwise free" scheme. This is an owner decision; the plan assumes a toggle on both devices first, with hold-to-rotate as a follow-up option.

**Focus and ownership constraints.** *Source (`plugin.cpp`, `focused()`):* the Camera policy treats any open menu flagged `kUsesCursor`, `kUsesMenuContext` or `kModal` as a focused menu and suspends its own gameplay behaviour. A cursor overlay implemented as a native cursor-using menu would therefore suspend the very mode that opened it. The implementation needs a narrowly scoped exception for the Camera's own overlay (identified by its menu name and flags, never by "any cursor menu"), while every native menu and dialog keeps precedence over the overlay. Target ownership also needs a rule, because hover supplies a candidate every frame while cycling supplies one per press: the plan adopts "cycling latches the chosen target until meaningful pointer or stick movement, target invalidation or mode exit", with the latch owned by the Camera module and pushed through the injection API. Leaving cursor mode must restore mouse and right-stick camera control in the same frame and hide the overlay; if the injection provider is absent or reports unavailable, cursor mode refuses to enable rather than showing a cursor that selects nothing.

**Injection path.** Three options, in order of preference: (1) upstream a small "external target provider" API to BTPS; (2) maintain a GPL-3 fork of BTPS with that API, shipped as a separate external package like the GPL minimap fork; (3) replace BTPS with an original selection plugin (duplicates R1 work, rejected unless 1 and 2 fail). The Camera module stays MIT and talks to the provider through its exported API, mirroring the SmoothCam/TDM pattern.

## R3 — Lock-on: reuse TDM target lock

**Why it is currently blocked.** The Camera module takes `RequestDisableTargetLock` at data load (`plugin.cpp`), and its policy prerequisites require `!GetTargetLockState()`, because TDM's lock writes camera yaw and pitch and would fight the held-pitch filter ([architecture](../ARCHITECTURE.md#adapter-boundary-and-settings-restoration)).

**What the source actually does.** *Source (`DirectionalMovementHandler::LookAtTarget`):* each frame while locked, TDM writes `ThirdPersonState::freeRotation.x` only if `fTargetLockYawAdjustSpeed > 0`; it **always** sets the player's pitch toward the target and adds the same delta to `freeRotation.y`; it then smooths `freeRotation.y` toward the target only if `fTargetLockPitchAdjustSpeed > 0`. With both speeds at 0 there is no yaw write, but there is still a per-frame player-pitch write plus a compensating camera-relative pitch write. The **hypothesis** is that the two cancel so the camera's world pitch (`player pitch − freeRotation.y`, which is what the held-pitch filter measures) is unchanged; that is an orientation-preservation claim about the net result, not a proven absence of camera writes, and it needs runtime confirmation through the lifecycle trace before the policy relies on it. `uTargetLockMode = kRelaxed` additionally leaves mouse look untouched; in `kLocked` mode the look hook swallows mouse movement and uses it to switch targets.

**The disable lease is not synchronous.** *Source (`ModAPI.cpp`, `DirectionalMovementHandler::Update`):* `RequestDisableTargetLock` only records the owner and sets a force-disable flag (it can also answer `MustKeep`). The flag is acted on in `UpdateTargetLock`, which is called from `Update()`, and `Update()` returns immediately while `UI::GameIsPaused()`. A lease taken when a menu opens is therefore not honoured until gameplay resumes; if the Camera module releases the lease on menu close before TDM has run, the target can still be locked. A correct handoff keeps the lease until `GetTargetLockState()` reports unlocked (or fails closed when the interface is unavailable), requires a fresh lock input after any interruption, and is tested on quick menu open/close, dialogue, loading, death, F6 and F8. TDM's lock settings are MCM values that the user can change live; the Camera module already re-reads TDM's settings file on menu close for the yaw-adjust guard, and the same mechanism must either refuse the lock state (suspend the policy) or re-apply the fragment when the adjust speeds or aim types differ from the declared values.

**Why it fixes the ranged FAIL.** *Source (`Hooks::ProjectileHook`):* while locked, player arrows and missiles with `uTargetLockArrowAimType`/`uTargetLockMissileAimType = kPredict` get their launch velocity solved toward the target point once (`kHoming` re-aims every tick). This ignores the camera entirely, which is precisely the Phase 1 overhead-aim failure mode (projectiles follow the camera ray into the ground). SmoothCam's own `useProjectileFixes` aims along the camera pitch and does **not** help from an elevated view; it is arrows-only.

**Target selection and switching.** *Source:* `FindTarget` prefers the actor under the crosshair, else the closest valid actor (alive, hostile if `bTargetLockHostileActorsOnly`, in line of sight, within `fTargetLockDistance`); manual presses use a distance-times-angle score. Switching uses the right thumbstick, mouse delta over a sensitivity threshold (only in `kLocked`), or the scroll wheel (`bTargetLockUseScrollWheel`). The wheel collides with SkyCRPG zoom and the stick with yaw; the fragment must disable the colliding inputs and the plan must validate the remaining ones. `bAutoTargetNextOnDeath` exists.

**API.** *Source (`TrueDirectionalMovementAPI.h`, V5):* `GetTargetLockState`, `GetCurrentTarget`, `RequestDisableTargetLock`/`ReleaseDisableTargetLock`, `RequestYawControl`/`SetPlayerYaw`. There is **no** API to start a lock, choose a target or change settings; those remain MCM/INI settings, which the project already manages as a merged fragment.

**Reticle.** *Source:* TDM's lock reticle is drawn through TrueHUD's API (`TDM_Widgets.swf`); without TrueHUD there is no reticle and `bTargetLockHideCrosshair` hides the crosshair. TrueHUD's 1.7.104 build is **unverified**. Camera-only installs need either TrueHUD as an optional external dependency or an original minimal lock indicator; the UI module must not become a Camera requirement.

**Other lock-on mods.** *Web:* himika's Lock-On (LE), LockonSSE/Simple Lock-On (1.5.x era, unsupported), TDM Lock-on Fixes (reticle positions), Precision (hit detection only), AIM FIX (crosshair offsets). No maintained alternative; nothing to reuse beyond TDM.

## R4 — Fixed height and occluder fade: staged original work

**Why the camera pulls in today.** *Source:* SmoothCam's collision is unconditional: `thirdperson.cpp` casts player→side-offset (hull 30) then `BaseThird::ComputeRaycast` (hull 15) through the engine camera caster (AE ID 33007) and moves the camera to the hit. There is no config toggle, no per-layer filter and no fork licence (the [reuse audit](../REUSE_RESEARCH.md) records only the API-header permission). The opt-in DYL-157 compression policy then lowers pitch/zoom on top of that; it is the "zoom in under beams" the owner dislikes and defaults OFF.

**Ways to stop the pull-in without a second transform writer.**

1. **Detour the engine camera caster** (AE ID 33007) while the SkyCRPG policy is eligible: call the original, then discard hits that the policy classifies as fade-able occluders (for example overhead hits whose normal points down and whose goal position is still in open space), restoring the requested end point. SmoothCam remains the only transform writer; it simply sees "no hit". This keeps F8/native behaviour when the policy is off. **Unverified:** the function's full contract (the DYL-157 audit already noted a write through the camera context before the cast) and that SmoothCam tolerates a reported miss where the goal is inside thin geometry.
2. **Collision layers.** `NiAVObject::SetCollisionLayer` on an occluder's 3D or editing `bhkCollisionFilter::layerBitfields` for the camera layer. Rejected as the primary route: beams are frequently part of the same mesh as walls, changing a layer also changes actor collision, and the camera phantom's actual layer is unverified.
3. **Take camera control** (`RequestCameraControl`) and own collision. This is the "original controller" route explicitly deferred in Phase 1; it also means owning interpolation and every special state. Not recommended for this phase.
4. **Camera Studio** (Nexus 196829, GPL-3 + MPL, Improved Camera NG fork, states SE 1.5.97–1.7.104) adds an isometric third-person mode. *Web:* no statement about collision, occluders or ceilings. Worth one evaluation session as an alternative provider, not a plan dependency.

**Making occluders see-through.** *Web (source read from `src/Hook.h`, `src/Hook.cpp`, `src/Settings.h`):* the only precedent is **Skyrim Camera Disocclusion System** (machinegod420, Nexus 178575, GPL-3, May 2026): a centre ray plus a rotating ring of rays from camera to player (two ring rays per frame, hits linger 2 s, up to four marched hits per ray), accepting only `kStatic`/`kAnimStatic` hits that are not floor-like, then **near-clipping the occluder per draw call** by rewriting the projection near plane inside the `BSBatchRenderer::RenderPassImmediately` call site. That render hook carries **both SE and AE relocation IDs** (`RelocationID(100852, 107642)` with call-site offsets `0x29E`/`0x28F`), so it is not SE-only; which AE build the `0x28F` offset was taken from is not stated, and 1.7.104 is **unverified**. The three occlusion-plane hooks (build step, second plane-add, per-plane eye test) **are SE-only** and are skipped elsewhere (`PlaneHooksSupported()` = `REL::Module::IsSE()`); `UseLegacyStrip=1` instead deletes planemarker references at cell load, which the author offers "for A/B or on AE/VR". Room culling is handled by a `BSMultiBoundRoom::QPointWithin` vtable hook with selectable **room-seeding modes**: 0 vanilla, 1 seed only the player's room, 2 (default) seed the rooms the camera-to-player sightline crosses (four point tests), 3 seed every room within `RoomSeedDistance` of the player while see-through is active, which the author says costs about 30 fps. The earlier statement that it "forces every room visible" applied only to mode 3. The author reports clip artefacts ("doesn't fade very well") and Community Shaders incompatibility. It is a reference for detection, clipping and culling strategies, not a drop-in dependency, and the spike must evaluate its actual approaches on 1.7.104 rather than an approximation of them.

Mechanisms a 1.7.104 implementation can try, in order of cost:

| Mechanism | What it does | Status |
| --- | --- | --- |
| `NiAVObject::SetAppCulled` on the occluder's 3D | Hides the reference outright (CRPG cutaway, no fade) | Known to work for hiding; pops; needs hysteresis and restore on every lifecycle exit. |
| `NiAVObject::UpdateMaterialAlpha` | Sets `materialAlpha` on each geometry's lighting shader material; this is how actor alpha works | **Unverified for statics**: a static without an alpha-blending `NiAlphaProperty` may ignore it, and the engine may rewrite alpha from `BSFadeNode::currentFade`. Spike required. |
| Add/modify `NiAlphaProperty` and clear render passes | Forces alpha blending on the occluder | Unverified; sorting artefacts likely; per-object cost. |
| Near-plane clipping per draw (Disocclusion approach) | Clips the occluder without materials | SE and AE relocation IDs exist; the AE call-site offset must be confirmed on 1.7.104; artefacts documented by its author. |
| Shader-level dither (Community Shaders feature) | Proper fade | Out of scope: requires a renderer dependency. |

These are not interchangeable. Hiding removes the geometry entirely, near-plane clipping cuts it, and transparency keeps visual context while revealing the player. The owner asked for the last; if the spike cannot demonstrate it, the outcome is an owner decision between the alternatives, not an automatic substitution.

**Interior culling risk.** *Web (CK wiki):* when the camera leaves all room bounds, the engine draws only what portals expose; interiors have no outer shell. A camera held above a low rock ceiling therefore shows nothing. Disocclusion's `QPointWithin` hook with its seeding modes is the only known workaround; its default seeds only the rooms crossed by the camera-to-player line, and its author measured the broad mode at roughly 30 fps. Hence the staging below: keep native SmoothCam collision for true enclosure (the preferred camera position lies inside solid geometry or outside the room) and only ignore **thin overhead occluders** that are positively identified as safe (far side open space, inside the current room). Full see-through through walls and ceilings is a separate stage that needs its own feasibility evidence and its own owner approval, even if the spike succeeds.

**The "jarring pop" already observed.** The owner reported low overhead objects disappearing at a threshold. The research found no near-camera fade for statics; the likely cause is the near clip plane (`fNearDistance`, default 15) as the collided camera passes through the beam. Keeping the camera away from the beam (R4 stage 1) removes the trigger rather than the symptom.

## Input budget

Three new bindings are needed on controller (lock toggle, cycle/tab, cursor-mode toggle) and the Camera module refuses natively mapped buttons. TDM's default lock toggle is a short press of the POV button (`bTargetLockUsePOVSwitchGamepad`, `fTargetLockPOVHoldDuration`), which the fragment currently disables; re-enabling it shares R3 with native POV hold. Cycle and cursor mode have no proven free button. This is an owner decision recorded in the plan, not an engineering default.

## Licensing notes

BTPS (GPL-3.0-or-later, no stated exception), TDM (GPL-3 **with** modding and linking exceptions), Disocclusion (GPL-3) and Camera Studio (GPL-3 + MPL) are all external. TDM's exceptions are what make the current API-header use straightforward; they do not transfer to BTPS. Separating binaries and talking through an exported API does **not** by itself settle whether the MIT Camera module plus a GPL BTPS fork form one combined work. MIT is GPL-compatible, so several integration structures may be viable, but the actual API/linking boundary (header copying, message passing, who loads whom) needs a written licensing and distribution assessment before implementation. The plan therefore separates three permissions: (1) evaluating and shipping a configuration for **stock** BTPS as an external, pinned dependency, which needs no fork; (2) requesting an upstream target-injection API or an explicit exception from the BTPS author; (3) a fork, only with the exact licence and source revision pinned, corresponding-source obligations documented, and the boundary assessment accepted. Copying Disocclusion's or TDM's code into the Camera module is not compatible with D015 and is not proposed; the Camera module stays MIT and does not require relicensing on the evidence so far.
